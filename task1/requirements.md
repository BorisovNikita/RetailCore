# RetailCore - ключевые функциональные требования, архитектурно значимые нефункциональные требования, список ограничений и допущений

## 1. Ввведение

Документ фиксирует предварительно собранные знания по итогам анализа описания RetailCore, PlantUML-диаграммы, описания технологического стека и имеющихся интервью с бизнес-заказчиком и руководителем поддержки.

Состояние требования:
- **Точное** - прямо упоминалось.
- **Гипотеза** - возможно нужно подтвердить.

## 2. Ключевые функциональные требования

| № | Требование | Статус | Источник (комментарий к требованию) |
|---|---|---|---|
| ФТ-01 | Единое внутреннее представление заказа: состав, канал, оплата, доставка, текущее состояние, клиентский статус, история изменений и отклонений | Точное / гипотеза | Поддержка: карточка заказа не является единым источником правды |
| ФТ-02 | Разделение клиентских статусов и внутренних технических состояний заказа | Точное | Поддержка: статусы слишком непоказательные для клиента и недостаточные для оператора |
| ФТ-03 | Формализованная модель жизненного цикла заказа с переходами, причинами отклонений и правилами обработки исключений | Точное / гипотеза | Фактическое поведение расходится с документацией |
| ФТ-04 | Прослеживаемость изменений заказа: срок доставки, состав, способ доставки, оплата, возвраты, отмены, ручные корректировки | Точное | Поддержка: нужна понятная история, а не разрозненные технические следы |
| ФТ-05 | Автоматическая маршрутизация заказов, выпавших из стандартного потока, в нужный сценарий обработки | Гипотеза | Поддержка: значительная часть практики держится на опыте людей |
| ФТ-06 | Поддержка "checkout": расчёт цены, скидок, промо, выбор доставки и оплаты, подтверждение заказа | Точное | Описание, PlantUML диграмма, интервью бизнеса |
| ФТ-07 | Единая модель каналов продаж: сайт, мобильные каналы, маркетплейсы как вариации общей модели, а не набор независимых исключений | Точное / гипотеза | Бизнес: канал часто тянет собственные ветки поведения |
| ФТ-08 | Унифицированная интеграция с внешними партнёрами: маркетплейсы, платёжные провайдеры, службы доставки | Точное / гипотеза | PlantUML: разные способы интеграции, внешние зависимости |
| ФТ-09 | Единый слой событий и данных по заказам, статусам, платежам и логистике для аналитики и отчётности | Точное / гипотеза | Бизнес: разные функции видят разные цифры |
| ФТ-10 | Инструменты поддержки: единая карточка заказа, поиск, ручные действия с аудитом | Точное | Поддержка, PlantUML |
| ФТ-11 | Управление возвратами, частичными отменами, повторными оплатами и компенсациями как отдельными сценариями | Точное | Поддержка: сложные возвраты и частичные отмены — болезненная зона |
| ФТ-12 | Поддержка новых сервисов: персонализация, гибкие предложения, партнёрские сценарии | Точное как цель | Бизнес: планы на год |
| ФТ-13 | Аудит ручных изменений статусов, атрибутов и служебных флагов | Точное / гипотеза | Поддержка: старшие специалисты могут менять технический статус |

## 3. Архитектурно значимые нефункциональные требования

| ID | Требование | Статус | Ответственные |
|---|---|---|---|
| НФТ-01 | Устойчивость критического order flow: оформление, оплата, подтверждение, передача в доставку | Точное | Нет SLA/SLO. Уточнить у бизнеса, эксплуатации |
| НФТ-02 | Производительность checkout и операций со статусами | Точное, важное | Нет p95/p99, RPS/TPS. Уточнить у бизнеса, техлида, эксплуатации |
| НФТ-03 | Масштабируемость до требуемых значений на сезонных пиках и распродажах | Точное | Нет пиковых значений нагрузки. Уточнить у эксплуатации и бизнеса |
| НФТ-04 | Консистентность данных между заказом, оплатой, логистикой и статусами | Точное | Нет правил: где точная, где гибкая. Уточнить у техлида, бизнеса |
| НФТ-05 | Наблюдаемость: метрики, логи, трассировки, бизнес-события, объяснимость состояния заказа | Точное | Нет требований к глубине и сроку. Уточнить у поддержки, эксплуатации |
| НФТ-06 | Восстанавливаемость после сбоев | Точное, важное | Нет RTO/RPO. Уточнить у эксплуатации и бизнеса |
| НФТ-07 | Постепенный отказ от Oracle и снижение зависимости от зарубежных компонентов | Точное | Нет сроков, приоритетов, допустимой стоимости. Уточнить у спонсора, инфраструктуры |
| НФТ-08 | Обратная совместимость и возможность отката при поэтапной трансформации | Точное | Нет правил деградации и октата. Уточнить у бизнеса и эксплуатации |
| НФТ-09 | Архивирование и сохранение данных | Точное | Архивирование частичное и несистемное. Нет политики retention. Уточнить у эксплуатации, аналитики, комплаенса |
| НФТ-10 | Снижение доли ручных и «героических» операций между командами | Точное | Нет метрики. Уточнить у поддержки и бизнеса |

## 4. Ограничения

| ID | Ограничение | Статус |
|---|---|---|
| 01 | Система размещена on-premise на физических серверах; виртуализация ограниченна | Точное |
| 02 | Центральная БД Oracle содержит десятки ТБ данных, часть бизнес-логики и интеграционный слой | Точное |
| 03 | Java-монолит - центральный контур обработки заказов; вокруг есть Python и .NET сервисы | Точное |
| 04 | Взаимодействие смешанное: прямые вызовы, обмен через БД, async/batch | Точное |
| 05 | Нельзя останавливать бизнес и делать одномоментную миграцию | Точное |
| 06 | Существует большая инсталляционная база процессов, команд и интеграций | Точное |
| 07 | Внешние партнёры со своими сервисами: маркетплейсы, платёжные провайдеры, службы доставки | Точное |
| 08 | Есть запрос на импортонезависимость, но не ценой остановки ключевых процессов | Точное |

## 5. Допущения

| ID | Допущение | Что проверить |
|---|---|---|
| 01 | Боли поддержки отражают системные проблемы архитектуры, а не только локальные процессы | Интервью с поддержкой и заказами |
| 02 | Бизнес-приоритеты из интервью с директором цифровых продаж актуальны для спонсора | Интервью со спонсором |
| 03 | Java-монолит и Oracle - основные источники связанности и сложности изменений | Интервью с техлидом |
| 04 | Поэтапное выделение границ возможно без полной остановки развития | Технический анализ и интервью |
| 05 | Промежуточная бизнес-ценность достижима на каждом этапе | Совместно с бизнесом |
| 06 | Часть legacy-сценариев можно временно не менять, если они стабильны | Интервью с заказами и техлидом |
