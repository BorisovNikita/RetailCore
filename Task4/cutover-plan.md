
#План переключения: включение публикации событий заказа

> Назначение документа: описать конкретное включение публикации событий заказа в рабочем контуре: цель, условия запуска, роли, пошаговый сценарий, состояние данных, наблюдаемость, сравнение нового поведения со старым и rollback-сценарий.

## 0. Паспорт cutover-плана

| Поле | Значение |
|---|---|
| Название перехода | Включение публикации событий заказа из монолита в слой событий |
| Связанный этап roadmap | Этап 1. Слой событий заказа |
| Связанная точка трансформации | Точка 3. Слой событий заказа |
| Тип переключения | Запись (публикация событий) / интеграция |
| Временное окно | Период низкой нагрузки (например, вторник, 02:00–04:00 МСК) |

| Зона воздействия | 5% заказов сайта и мобильного приложения, регион «Центр» |
| Ответственный за go / no-go | Технический лидер ядра |
| Автор документа | Самый главный архитектор по самым главным архитекторам |

## 1. Цель переключения

> Цель переключения — включить публикацию бизнес-событий заказа из Java-монолита в слой событий для пилотной доли заказов (5% сайта и мобильного приложения, регион «Центр»). После переключения система должна публиковать события по всем пилотным заказам с задержкой не более 2 секунд и долей потерь не более 1%. Данные в Oracle остаются источником истины и не меняются. Старый контур (без публикации) сохраняется как резерв и fallback до завершения периода наблюдения. Потребители событий на этом этапе — только мониторинг и технический дашборд; read-model, уведомления и ACL подключаются на следующих этапах.

## 2. Объём переключения

### 2.1. Включаем

- Публикация событий `order.created`, `order.status_changed`, `payment.session_created`, `delivery.slot_reserved` из монолита.
- Публикация в слой событий (очередь/шина).
- Мониторинг публикации и доставки.
- Метрики по доле заказов с событиями.

### 2.2. Не включаем

- Потребители событий (read-model, уведомления, ACL, аналитика) — подключаются на следующих этапах.
- Изменение ядра монолита (транзакция create order не меняется).
- Изменение логики в Oracle.
- Все остальные 95% заказов.

### 2.3. Критерии успешного переключения

| Критерий | Целевое значение | Где проверяем | Кто подтверждает |
|---|---:|---|---|
| Доля пилотных заказов с событиями | ≥ 99% | Слой событий, метрика | Техлид |
| Задержка публикации события | ≤ 2 с (p95) | Мониторинг очереди | Эксплуатация |
| Доля потерянных событий | ≤ 1% | Сверка событий и заказов | Техлид |
| Деградация ядра | нет | Метрики Oracle и checkout | Эксплуатация |
| Дубли событий | ≤ 0,5% | Сверка идентификаторов | Техлид |

## 3. Условия запуска: go / no-go

| Условие | Тип | Как проверяем | Порог / ожидаемое состояние | Статус | Ответственный |
|---|---|---|---|---|---|
| Слой событий развёрнут и доступен | Техническое | Health-check очереди/шины | Доступен, latency ≤ 100 мс | go | Эксплуатация |
| Контракты событий утверждены | Техническое | Ревью схем | Схемы зафиксированы | go | Архитектор |
| Публикация протестирована на staging | Техническое | Тестовый прогон | 100% событий опубликовано | go | Разработчик |
| Мониторинг публикации работает | Наблюдаемость | Проверка дашборда | Метрики видны | go | Эксплуатация |
| Алерты настроены | Наблюдаемость | Проверка правил | Алерты срабатывают | go | Эксплуатация |
| Feature flag публикации доступен | Техническое | Проверка конфигурации | Флаг управляем | go | Разработчик |
| Rollback-сценарий протестирован | Техническое | Прогон на staging | Отключается без потерь | go | Техлид |
| Ядро не менялось | Техническое | Diff релиза | Изменений в ядре нет | go | Техлид |
| Поддержка проинформирована | Коммуникация | Проверка канала | Инструкция отправлена | go | Поддержка |
| Бизнес-владелец согласовал окно | Операционное | Согласование | Окно подтверждено | go | Бизнес-владелец |
| Ответственный за go/no-go на связи | Операционное | Проверка канала | На связи | go | Техлид |

**Правило:** если хотя бы одно критичное условие не выполнено, решение — `no-go`.

| Data / DBA | Проверка отсутствия изменений в Oracle | Контроль нагрузки | Сверка данных | Канал DBA |

## 5. Состояние данных до переключения

| Данные / сущность | Источник истины до переключения | Источник истины после переключения | Подготовка до cutover | Проверка консистентности | Что делаем при расхождении |
|---|---|---|---|---|---|
| Заказ | Oracle | Oracle (не меняется) | Нет | Сверка заказов и событий | Остановить публикацию, разобрать расхождение |
| Статус заказа | Oracle | Oracle (не меняется) | Нет | Сверка статусов | Остановить публикацию |
| Платёжная сессия | Oracle | Oracle (не меняется) | Нет | Сверка событий оплаты | Остановить публикацию |
| Логистический слот | Oracle | Oracle (не меняется) | Нет | Сверка событий доставки | Остановить публикацию |
| События | Не существуют | Слой событий | Схемы утверждены | Сверка с заказами | Отключить публикацию, разобрать потери |

**Важно:** Oracle остаётся источником истины; слой событий — производный. Потери событий не влияют на транзакционное состояние заказа.

## 8. Проверки после переключения

### 8.1. Технические проверки

| Проверка | Ожидаемое значение | Источник | Что делать при нарушении |
|---|---:|---|---|
| Доля заказов с событиями | ≥ 99% | Дашборд событий | Откатить публикацию |
| Задержка публикации (p95) | ≤ 2 с | Дашборд очереди | Откатить |
| Глубина очереди | ≤ 1000 | Дашборд очереди | Снизить долю пилота |
| Ошибки публикации | ≤ 0,1% | Логи монолита | Откатить |
| Latency checkout (p95) | без изменений | Дашборд монолита | Откатить |

### 8.2. Проверки данных

| Проверка | Ожидаемое значение | Метод сверки | Что делать при расхождении |
|---|---:|---|---|
| Количество событий | Соответствует числу пилотных заказов | SQL + сверка ID | Остановить, разобрать |
| События по типам | Все 4 типа публикуются | Сверка по типам | Остановить, доработать |
| Дубли | ≤ 0,5% | Проверка ID | Разобрать, добавить дедупликацию |
| Потери | ≤ 1% | Сверка заказов и событий | Остановить, разобрать |

### 8.3. Проверки поведения нового контура относительно старого

| Сценарий | Ожидаемое поведение нового контура | Как сравниваем со старым | Допустимое расхождение | Решение при отклонении |
|---|---|---|---:|---|
| Создание заказа | Событие `order.created` публикуется после транзакции | Shadow mode (события пишутся, но не читаются) | ≤ 2 с задержки | Откатить |
| Изменение статуса | Событие `order.status_changed` публикуется | Сверка с Oracle | Дубли ≤ 0,5% | Откатить |
| Создание платёжной сессии | Событие `payment.session_created` публикуется | Сверка с Oracle | Дубли ≤ 0,5% | Откатить |
| Резервирование слота | Событие `delivery.slot_reserved` публикуется | Сверка с Oracle | Дубли ≤ 0,5% | Откатить |

### 8.4. Операционные проверки

| Проверка | Кто проверяет | Ожидаемое состояние | Что делать при проблеме |
|---|---|---|---|
| Дашборд доступен поддержке | Поддержка | Дашборд открывается | Сообщить SRE |
| Инструкции поддержки применимы | Поддержка | Инструкция актуальна | Обновить |
| Пользовательские уведомления не затронуты | Поддержка | Уведомления не менялись | Остановить |
| Обращения по статусу | Поддержка | Без роста | Остановить, разобрать |

## 9. Критерии стабилизации после переключения

| Период наблюдения | Что должно быть стабильно | Порог | Решение |
|---|---|---:|---|
| Первые 15 минут | Доля заказов с событиями, задержка, ошибки | ≥ 99%; ≤ 2 с; ≤ 0,1% | Продолжить / откатить |
| Первый час | Задержка, дубли, нагрузка на ядро | ≤ 2 с; ≤ 0,5%; без деградации | Продолжить / ограничить долю |
| Первый день | Доля заказов с событиями, дубли, потери | ≥ 99%; ≤ 0,5%; ≤ 1% | Расширять / оставить 5% |
| Первая неделя | Все метрики стабильны | В норме | Расширять / пересмотреть roadmap |

## 10. Rollback-сценарий

### 10.1. Условия запуска rollback

| Триггер rollback | Порог | Кто принимает решение | Максимальное время реакции |
|---|---:|---|---|
| Доля заказов с событиями падает | < 95% в течение 5 минут | Техлид | 5 минут |
| Задержка публикации растёт | p95 > 5 с в течение 5 минут | Техлид | 5 минут |
| Дубли событий растут | > 1% | Техлид | 10 минут |
| Потери событий растут | > 1% | Техлид | 10 минут |
| Деградация ядра | p95 checkout +20% в течение 5 минут | Эксплуатация / Техлид | 5 минут |
| Глубина очереди растёт | > 5000 | Эксплуатация | 10 минут |

### 10.2. Шаги rollback

| Шаг | Действие | Ответственный | Проверка результата | Что делать с данными, созданными в новом контуре |
|---:|---|---|---|---|
| 1 | Отключить feature flag публикации | Разработчик | Публикация остановлена | События в очереди оставить, потребители их не читают |
| 2 | Проверить, что ядро работает без публикации | Техлид | Checkout работает | — |
| 3 | Проверить отсутствие роста ошибок в ядре | Эксплуатация | Метрики в норме | — |
| 4 | Сверить события с заказами за окно | DBA / Техлид | Расхождения зафиксированы | Спорные события пометить |
| 5 | Сообщить поддержке и бизнесу | Техлид | Информация отправлена | — |
| 6 | Принять решение: повтор / доработка / отказ | Техлид + Бизнес | Решение зафиксировано | — |

### 10.3. Состояние после rollback

| Область | Ожидаемое состояние после отката | Как проверяем |
|---|---|---|
| Трафик | Ядро работает как до переключения | Checkout работает |
| Данные | Oracle — источник истины, без изменений | Сверка заказов |
| Очереди / события | События в очереди не обрабатываются | Проверка потребителей |
| Пользовательские статусы | Без изменений | Проверка UI |
| Поддержка | Инструкция о rollback | Опрос поддержки |
