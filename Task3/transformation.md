## 1. Краткое резюме трансформации

RetailCore должен поддержать рост нагрузки, ускорить запуск коммерческих изменений и снизить долю ручных операций, не останавливая критический order flow и не отказываясь от Oracle одномоментно. В текущем состоянии этому мешают: высокая связность Java-монолита и Oracle, смешанные интеграции (REST, очереди, обмен через БД), неявная модель статусов, ручные корректировки, отсутствие единого слоя событий заказа и аналитической нагрузки на операционную БД.

Для первого этапа выбраны точки трансформации, не затрагивающие ядро оформления заказа и платёжную оркестрацию напрямую: **модель чтения карточки заказа**, **двухуровневая модель статусов**, **единый слой событий заказа**, **унифицированный интеграционный слой для логистики**, **сервис уведомлений** и **вынос аналитических выгрузок из операционной Oracle**.

Целевая архитектура не заменяет монолит целиком, а окружает его управляемыми границами: read-model для поддержки и аналитики, канонический поток событий, ACL для внешних партнёров. Checkout, pricing и payment orchestration остаются в монолите на этом этапе - их изменение признано слишком рискованным.

## 3. Краткое описание AS-IS

| Область | Текущее состояние | Почему это важно |
|---|---|---|
| Бизнес-процесс | Заказ проходит через монолит; статусы, промо и логистика распределены по нескольким слоям | Ограничивает прозрачность и скорость изменений |
| Компоненты | Java-монолит, Oracle (данные + логика + интеграции), .NET-сервис, Python-аналитика, async/batch | Высокая связность, скрытые зависимости |

| Интеграции | REST, очереди, обмен через staging-таблицы, batch, CSV | Нет единого контура, неоднородная семантика |
| Эксплуатация | Ручные корректировки статусов, ручные настройки приоритетов доставки | Плохо масштабируется на пиках |

## 4. Ограничения и допущения

| Тип | Формулировка | Влияние на архитектуру |
|---|---|---|
| Техническое | Нельзя останавливать критический order flow; нет окна на взрывную нагрузку | Только поэтапные изменения с возможностью отката |
| Техническое | Oracle остаётся центральным узлом на этом этапе | Полный отказ от Oracle отложен |
| Инфраструктурное | On-prem, ограниченная виртуализация, ресурсы близки к пределу | Новые компоненты должны быть лёгкими и не перегружать инфраструктуру |
| Организационное | Несколько команд с разными подходами; знания у людей | Изменения должны снижать, а не увеличивать зависимость от экспертизы |
| Доменное | Партнёры имеют собственные SLA и задержки | Нельзя включать партнёров в мгновенное подтверждение заказа |
| Импортонезависимость | Отказ от Oracle важен, но не ценой остановки процессов | Двигаться через read-model и события, а не через прямую замену БД |
| Допущение | Read-model и события можно построить без изменения ядра | Проверяется на этапе проектирования интеграций |
| Допущение | Поддержка и аналитика готовы перейти на новые источники данных | Требует подтверждения у владельцев |

## 5. Препятствия первого релиза

| Препятствие | Где проявляется | Влияние | Можно изменить сейчас? | Решение |
|---|---|---|---|---|
| Карточка заказа не единый источник правды | Поддержка, admin tools | Повторные обращения, эскалации | Да | Точка трансформации: read-model карточки заказа |
| Статусы грубые для клиента и недостаточные для оператора | Statuses, UI, поддержка | Расхождение статусов, обращения | Да | Точка трансформации: двухуровневая модель статусов |
| Нет единого потока событий заказа | Монолит, аналитика, интеграции | Расхождения данных, нагрузка на Oracle | Частично | Точка трансформации: слой событий заказа |
| Смешанные интеграции логистики | Delivery Routing, .NET, Oracle | Хрупкость, дубли, ручные разборы | Частично | Точка трансформации: ACL для логистики |
| Аналитические выгрузки из операционной Oracle | Python jobs, BI | Нагрузка на ядро | Да | Точка трансформации: вынос аналитики на read-model |
| Нет сервиса уведомлений | Клиентский канал | Клиент не получает объяснений | Да | Точка трансформации: сервис уведомлений |
| Синхронные вызовы в checkout | Order API | Хрупкость при отказе партнёров | Нет на этом этапе | Ограничение: не трогаем checkout |
| Payment orchestration | Payment Orchestration | Критический путь | Нет на этом этапе | Технический долг, отдельный этап |
| Логика в Oracle packages | Pricing, Delivery Routing | Скрытая связанность | Нет на этом этапе | Технический долг, этап после read-model |

## 6. Точки трансформации

| № | Точка трансформации | Проблема AS-IS | Целевое изменение | Ограничения | Метрика | Владелец |
|---:|---|---|---|---|---|---|
| 1 | Read-model карточки заказа | Карточка не единый источник правды | Отдельная модель чтения для поддержки и admin | Не меняет ядро заказа | Время сборки истории, число касаний | Команда заказов |
| 2 | Двухуровневая модель статусов | Статусы грубые и рассинхронизированы | Клиентский + внутренний статус, журнал переходов | Не меняет модель в Oracle сразу | Обращения по статусу, расхождения | Команда заказов + поддержка |
| 3 | Слой событий заказа | Нет канонического потока событий | Публикация бизнес-событий заказа/статусов/оплаты | Не меняет транзакцию create order | Доля заказов, покрытых событиями | Команда заказов + аналитика |
| 4 | ACL для логистики | Смешанные интеграции, дубли, retry | Единый контракт, retry, идемпотентность | Не меняет логику выбора маршрута в Oracle | Число дублей, ошибок интеграции | Команда логистики |
| 5 | Вынос аналитики на read-model | Аналитика читает операционную Oracle | Аналитика читает витрины из событий и read-model | Не отменяет Oracle, но снижает нагрузку | Доля запросов в операционную БД | Команда аналитики |
| 6 | Сервис уведомлений | Уведомлений нет | Единый сервис уведомлений с повторами и журналом | Не блокирует заказ | Доля доставленных уведомлений | Команда клиентского опыта |

### 6.1. Паспорт точки трансформации

#### Точка 1. Read-model карточки заказа

| Вопрос | Ответ |
|---|---|
| Бизнес-цель | Снизить нагрузку на поддержку и число эскалаций |
| Где в AS-IS | Admin tools, поддержка, Oracle |
| Что плохо | Оператор собирает картину из нескольких систем |
| Что меняется | Единая модель чтения по заказу с историей и статусами |

| Ограничения | Нельзя блокировать ядро; данные должны обновляться асинхронно |
| Метрика | Время сборки истории ≤ 5 с; число касаний −25% |
| Неуспех | Расхождения read-model и источника > 1% |

| Что не меняется | Внутренние технические статусы партнёров |
| Ограничения | Нельзя ломать существующие переходы |
| Метрика | Обращения по статусу −30% |
| Неуспех | Рост обращений после релиза |

|---|---|

| Что меняется | Публикация событий заказа, статусов, оплаты, доставки |

## 9. Целевая архитектура первого этапа

### Краткое описание TO-BE

Java-монолит остаётся центральным оркестратором заказа и источником транзакционных данных. Вокруг него появляются: **слой событий заказа**, **read-model карточки заказа**, **сервис уведомлений**, **ACL для логистики** и **витрины аналитики**, построенные из событий. Checkout, pricing и payment orchestration не меняются. Oracle остаётся, но перестаёт быть единственным источником чтения для поддержки и аналитики.

### Компоненты целевой архитектуры

| Компонент | Роль | Новый / существующий / изменяемый | Ответственность | Ограничения |
|---|---|---|---|---|
| Java-монолит | Ядро order flow | Существующий | Checkout, pricing, payment orchestration, статусы | Не меняется в первом этапе |
| Oracle | Транзакционные данные и логика | Существующий | Источник истины для заказа | Остаётся, но разгружается |
| Слой событий заказа | Публикация бизнес-событий | Новый | Канонический поток событий заказа, статусов, оплаты, доставки | События публикуются после транзакции |
| Read-model карточки заказа | Модель чтения для поддержки | Новый | Единое представление заказа с историей | Обновляется асинхронно |
| Сервис уведомлений | Канал информирования | Новый | Доставка уведомлений с повторами и журналом | Не блокирует заказ |
| ACL для логистики | Единый контракт интеграции | Новый | Retry, идемпотентность, нормализация | Логика маршрута остаётся в Oracle |
| Витрины аналитики | Модель чтения для BI | Новый | Отчёты строятся из событий и read-model | Не отменяет Oracle |
| Admin tools | Инструменты поддержки | Изменяемый | Работа через read-model, аудит ручных действий | Не меняет ядро |

### Изменение поведения

| Сценарий | AS-IS | TO-BE первого этапа | Что видно пользователю / оператору |
|---|---|---|---|
| Просмотр карточки заказа | Оператор идёт по нескольким системам | Единая карточка из read-model | Единая история и статусы |
| Статус заказа | Клиентский и внутренний не связаны | Двухуровневая модель | Понятный клиентский статус |
| События заказа | Нет канонического потока | Публикация в слой событий | Возможны аналитика и уведомления |
| Аналитика по заказам | Прямые SQL в операционную Oracle | Витрины из событий | Отчёты без нагрузки на ядро |
| Уведомления клиенту | Нет | Сервис уведомлений | Клиент получает объяснения |
| Интеграция с логистикой | Смешанная | ACL с retry и дедупликацией | Меньше дублей и ручных разборов |

## 10. Разрыв AS-IS → TO-BE

| Область | AS-IS | TO-BE первого этапа | Что нужно изменить |
|---|---|---|---|
| Процессы | Поддержка собирает картину вручную | Единая карточка заказа | Обучить поддержку, обновить инструкции |
| Данные | Нет канонической модели | Read-model и события | Ввести контракты событий, идентификаторы |
| Интеграции | Смешанные | ACL для логистики | Единый контракт, retry, идемпотентность |
| Состояния | Нет двухуровневой модели | Клиентский + внутренний | Описать переходы, журнал |
| Компоненты | Монолит и Oracle | + события, read-model, уведомления, ACL, витрины | Реализовать новые компоненты |
| Наблюдаемость | Ограниченная | Метрики по событиям, read-model, уведомлениям | Дашборды и алерты |
| Операционная модель | Ручные корректировки | Аудит и ограничение ручных действий | Регламенты и права |
